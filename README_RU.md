# BOOTLOADER_PLCJS_ETH_MODULE_STM32F407VGT6

Универсальный загрузчик для всех вариантов модулей PLCJS ETH (12di, 12do,
4rtd, 4aic, 4aiv, 4ao, ...). Прошивка идентична для всех плат; варианты
отличаются только зашитыми `PRODUCT_ID` / `HW_REVISION`
(см. [Сборка для вариантов модулей](#сборка-для-вариантов-модулей)).

Ethernet bootloader для модуля PLCJS 12-DI на базе `STM32F407VGT6`.

Бутлоадер предоставляет OTA-протокол обновления по `Modbus TCP`, сохраняет новый
образ во внутреннюю staging-область, проверяет `CRC32`, устанавливает образ в
область приложения и затем передает управление основной прошивке.

## Текущее состояние

Текущая версия загрузчика — **1.9**. Контракт памяти:

- базовый адрес bootloader: `0x08000000`
- базовый адрес приложения: `0x08040000`
- сектор metadata: `0x08020000`
- staging-область: `0x08080000 .. 0x080BFFFF` (непрерывное окно 256 KB)
- сектор настроек приложения: `0x080C0000`

Следующие сценарии проверялись на платах в предыдущих версиях. Для 1.8/1.9
выполнены host-тесты и сборки, а также проверка на реальных 12DI, 12DQ и 4RTD
(OTA каждого приложения, три модуля в загрузчике одновременно, таймаут
брошенной сессии, отказ SET_NET при занятом адресе, повреждённое/стёртое/
недописанное приложение при загрузке). Не проверено: реальное пропадание питания
посреди стирания/записи Flash (сброс по SWD обрабатывается только после
завершения операции с Flash и её не имитирует):

- цикл warm reset `app -> bootloader -> app`
- повторные циклы перехода без выключения питания
- полный OTA update по `Modbus TCP`
- отклонение образа с неверным `CRC`
- восстановление после прерванной OTA-сессии
- длительный тест стабильности ping в bootloader

## Основные возможности

- bare-metal `LwIP` (`NO_SYS = 1`) с `Modbus TCP` сервером на порту `502`
- OTA update в режиме single-client
- staging, проверка `CRC32` и установка в flash-область приложения
- хранение служебного состояния в отдельном flash-секторе metadata
- программный запрос из приложения на вход в bootloader после reset
- recovery path для прерванной установки и прерванной загрузки

## Разметка flash

Определена в `Application/flash/flash_map.h`.

| Область | Адрес | Размер | Назначение |
|---|---:|---:|---|
| Bootloader | `0x08000000` | 128 KB | Сектора 0-4 |
| Metadata | `0x08020000` | 128 KB | Сектор 5, состояние OTA/update |
| Application | `0x08040000` | 256 KB | Сектора 6-7 |
| Staging | `0x08080000` | 256 KB | Сектора 8-9 |
| App settings | `0x080C0000` | 128 KB | Сектор 10, используется main app |

Образ приложения должен содержать структуру `fw_header_t` по смещению `0x200` от
`APP_FLASH_BASE`. Бутлоадер читает `product_id` и `hw_revision` из самого бинарника
(не только из того, что сказал инструмент обновления) в трёх точках:
`FINALIZE_UPDATE`, верификация при установке, `BOOT_VERIFY_APP`.
См. [Заголовок прошивки](#заголовок-прошивки) ниже.

Константы идентификации (дефолты для варианта 12-DI/D4MG, настраиваются через CMake):

| Константа | Значение | CMake-флаг |
|---|---|---|
| `PRODUCT_ID_DEFAULT` | `0x504C1201` | `-DPRODUCT_ID=0x...` |
| `HW_REVISION_DEFAULT` | `0x010101` | `-DHW_REVISION=0x...` |
| `BOOTLOADER_VERSION` | `1.9` | — |
| `FW_MAX_BLOCK_SIZE` | `240` байт | — |

## Сетевая конфигурация

Адрес и MAC вычисляются из UID по тому же алгоритму, что и в приложении:

- IP: `169.254.<mac[4]>.<mac[5]>`, нулевые/255 октеты заменяются на 1/254
- netmask: `255.255.0.0`
- gateway: отсутствует
- порт `Modbus TCP`: `502`
- `Modbus unit id`: `1`

Текущие ограничения:

- адрес при старте детерминированный и не проверяется; адреса из PDP SET_NET
  проверяются с версии 1.9
- DHCP в bootloader отсутствует
- изменение IP через `Modbus TCP` не реализовано
- одновременно поддерживается только один TCP-клиент

PDP использует UDP/20556 и широковещательные запросы/ответы; разрешите входящий
UDP 20556 в firewall. IDENTIFY имеет фиксированный payload 38 байт, включая
имя 16 байт, и сообщает `inBoot=1`. SET_NET с MAC выбранного модуля меняет адрес
до следующего reset. Для SET_NET/REBOOT загрузчик требует ненулевой target MAC.

## Как работает вход в bootloader

Логика решения stay/boot реализована в `Application/boot/boot_entry.c`.

Bootloader остается активным, если выполняется хотя бы одно из условий:

1. приложение запросило вход в bootloader, записав `BOOT_REQUEST_MAGIC`
   в зарезервированную no-init ячейку RAM по адресу `0x2001FFF0`
2. установка была прервана
3. проверенный staging ожидает INSTALL либо сохранено состояние ошибки
4. прием прошивки был прерван и оставался в процессе
5. приложение помечено как невалидное
6. проверка векторов, идентификации, размера или CRC приложения не проходит

Программный запрос одноразовый: bootloader считывает RAM-флаг и очищает его при
входе.

## Машина состояний bootloader

Реализована в `Application/boot/boot_main.c`.

Основные состояния:

- `BOOT_START`
- `BOOT_CHECK_ENTRY`
- `BOOT_WAIT_COMMAND`
- `BOOT_RECEIVE_FW`
- `BOOT_VERIFY_STAGING`
- `BOOT_INSTALL_FW`
- `BOOT_VERIFY_APP`
- `BOOT_READY_TO_BOOT`
- `BOOT_ERROR`

Нормальный OTA-поток:

1. вход в `BOOT_WAIT_COMMAND`
2. получение `BEGIN_UPDATE`
3. стирание staging и переход в `BOOT_RECEIVE_FW`
4. прием всех блоков прошивки
5. `FINALIZE_UPDATE` проверяет `CRC32` staging-области **и** читает `fw_header_t` из самого бинарника
6. `INSTALL_UPDATE` копирует прошивку в область приложения и повторно проверяет заголовок
7. образ приложения проходит валидацию (CRC32 + заголовок прошивки)
8. bootloader передает управление приложению

## OTA-протокол по Modbus TCP

Обработчики OTA-регистров реализованы в `Application/modbus/fw_update_proto.c`.

Команды, записываемые в holding register `HR[0x0000]`:

- `1` - `BEGIN_UPDATE`
- `2` - `FINALIZE_UPDATE`
- `3` - `INSTALL_UPDATE`
- `4` - `ABORT_UPDATE`
- `5` - `REBOOT`

Часто используемые input-регистры:

- `IR[0x0000..0x0001]` - magic `0xB00710AD`
- `IR[0x0004]` - состояние bootloader
- `IR[0x0005]` - признак валидности приложения
- `IR[0x000A..0x000B]` - HW revision, `(major<<16)|(minor<<8)|patch`
- `IR[0x000C]` - последняя ошибка
- `IR[0x000D..0x000E]` - общее число блоков
- `IR[0x000F..0x0010]` - число принятых блоков
- `IR[0x0011..0x0012]` - размер образа
- `IR[0x0013..0x0014]` - `CRC32` образа
- `IR[0x0015]` - статус команды
- `IR[0x0016]` - признак валидности staging
- `IR[0x0017..0x0018]` - product ID установленного приложения
- `IR[0x0019..0x001B]` - MAC: по два байта на регистр, старший первым (BL 1.8+)

Значения статуса команды:

- `0` - `IDLE`
- `1` - `BUSY`
- `2` - `OK`
- `3` - `ERROR`

Известные коды ошибок:

- `1` - `PRODUCT_MISMATCH`
- `2` - `HW_REV_MISMATCH`
- `3` - `IMAGE_TOO_LARGE`
- `4` - `BLOCK_CRC`
- `5` - `IMAGE_CRC`
- `6` - `FLASH_ERASE`
- `7` - `FLASH_WRITE`
- `8` - `APP_VALIDATE`
- `9` - `UPDATE_TIMEOUT`
- `10` - `BLOCK_INDEX`
- `11` - `BAD_PARAMS`

## OTA-клиент

Опорный CLI-клиент: `tools/fw_update.mjs` (Node 18+). Согласованная GUI-утилита —
ModbusTool 1.3.15+. Исторический Python-клиент не является образцом текущей
политики проверки MAC.

Базовое использование:

```bash
node tools/fw_update.mjs status
node tools/fw_update.mjs update path/to/app.bin --mac 02:00:12:34:56:78
node tools/fw_update.mjs abort --mac 02:00:12:34:56:78
node tools/fw_update.mjs reboot --mac 02:00:12:34:56:78
node tools/fw_update.mjs app-bootloader
```

Параметры по умолчанию:

- желаемый IP bootloader для адресного SET_NET: `192.168.1.2`
- IP приложения: `192.168.1.10`
- порт: `502`
- unit id: `1`

Полезные опции:

- `--boot-ip` / `--ip` — переопределить адрес bootloader
- `--app-ip` — переопределить адрес приложения
- `--nic <ip>` — локальный IPv4 сетевого адаптера для PDP
- `--mac <aa:bb:..>` — MAC выбранного устройства

Клиент всегда проверяет MAC через PDP, затем через то же TCP-соединение,
по которому отправляет команды. Проверка повторяется после переподключения и
смены IP. Если MAC не указан, допустим только один найденный загрузчик.
Наблюдаемый конфликт IP останавливает операцию. Ответ bootloader magic по
указанному IP не позволяет обойти проверку.

Защищённые update/abort/reboot требуют BL 1.8+. Старые BL доступны для чтения
статуса, но скрытого fallback при записи нет; сам загрузчик обновляется отдельно
через SWD. Идентификация и версия берутся из заголовка `.bin`; необязательный
`--version 0xMMmm` должен совпадать с заголовком. MAC не является аутентификацией.

## Вход в bootloader из основного приложения

Парное приложение входит в bootloader, записывая `0xB007` в holding register
`118`, после чего делает warm reset с сохранением общего RAM-флага.

Пример с `pymodbus`:

```python
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient("192.168.1.10", port=502, timeout=5)
client.connect()
client.write_register(address=118, value=0xB007, device_id=1)
client.close()
```

Перед низкоуровневой записью HR118 проверьте MAC/IP приложения через PDP;
Node/Qt-клиенты делают это автоматически. Пример адресации:

- main app настроен на `192.168.1.10`
- BL по умолчанию использует link-local; `192.168.1.2` можно назначить через PDP

## Замечания по восстановлению

В BL 1.8 передача образа и установка различаются:

- Обрыв передачи не стирает старое приложение. После reset MCU нужны новый BEGIN
  и полная передача: bitmap хранится в RAM до FINALIZE. ABORT → REBOOT возвращает
  старое приложение только при сохранённой валидности.
- FINALIZE проверяет bitmap, CRC ровно `image_size` байт, заголовок и векторы.
  После успеха и после reset загрузчик ждёт INSTALL; автоматическая установка
  не разрешается. Старые metadata после одного FINALIZE трактуются так же.
- INSTALL повторно проверяет staging и сохраняет `install_in_progress=1`,
  `app_valid=0` до стирания application. После reset во время erase/copy
  установка начинается заново с проверенного staging, сеть инициализирована.
- Ошибка установки оставляет доступное по сети состояние ERROR. Возможны новый
  BEGIN или повторный INSTALL валидного staging. ABORT не восстанавливает
  стёртое приложение.
- Проверяются обязательные сохранения metadata и read-back. Формат остаётся
  одним сектором: потеря питания во время перезаписи может уничтожить последнюю
  запись. Невалидная metadata приводит к сетевому recovery, автоматическое
  продолжение тогда не гарантировано. Журнал отложен; сектора 10/11 не меняются.
- При установке и финальной проверке изменяющие Modbus-команды получают exception
  6 (device busy), не затирая статус текущей установки. PDP SET_NET/REBOOT также
  запрещены; IDENTIFY продолжает работать.
- Брошенная сессия обновления не держит плату в загрузчике вечно (1.9): если идёт
  приём блоков или проверенный staging ждёт INSTALL, а записей от клиента нет
  `FW_SESSION_TIMEOUT_MS` (120 с), сессия сбрасывается (`last_error =
  UPDATE_TIMEOUT`) и, если установленное приложение проходит полную проверку CRC,
  плата перезагружается в него. Без валидного приложения остаётся в загрузчике.
  Простаивающий загрузчик, запрошенный командой (без сессии), по таймауту не
  выходит. Проверено на 4RTD: клиент убит посреди передачи, приложение вернулось
  примерно через 2 минуты.
- PDP SET_NET применяется только после проверки адреса (1.9): три ARP-пробы
  (отправитель 0.0.0.0, интервал 200 мс) и ожидание 300 мс; ответы ловит
  `addr_probe_input()` на пути приёма. Если на адрес уже отвечает любая станция
  (ПК, ПЛК, другой модуль), ответ со статусом 1, адрес не меняется; иначе адрес
  применяется и подтверждается статусом 0 примерно через секунду. Повтор того же
  запроса или установка уже действующего адреса подтверждаются сразу. Проверено
  на ПК и двух других модулях.

Размер блока — 4..240 байт, кратный четырём; число блоков равно
`ceil(image_size/block_size)`. Последний блок имеет ровно остаточную длину.
Один блок передаётся одним FC16 начиная с `0x0100`. Идентичный повтор успешен
без повторной записи и увеличения счётчика; изменённый повтор отклоняется.
Read-back сравнивается до установки бита bitmap. FINALIZE проверяет каждый бит.

Активного TCP-клиента новое соединение не вытесняет. Таймаут без полноценных
запросов — 30 секунд, незавершённого ADU — 5 секунд; включён keepalive. Разрыв
TCP сам не отменяет загрузку или установку. RX использует TCP backpressure,
неотправленные ответы сохраняются при временном заполнении TX-очереди.
Текущие клиенты после неудачной передачи начинают новую сессию через BEGIN,
автоматического продолжения блоков в них нет. Стирание Flash может задерживать
сеть; таймаут запроса обновляющего клиента — 15 секунд. Тайминги требуют стенда.

Ethernet TX ждёт завершения DMA; после ошибки MAC/DMA восстанавливаются до
повторного использования буфера, без reset KSZ8863. Перед переходом в приложение
останавливаются TIM7 и DMA, SysTick отключается после RCC deinit, очищаются
pending IRQ; после смены MSP выполняется только ассемблерный переход.

Host-тесты запускаются нативным компилятором, не ARM toolchain:

```sh
cmake -S tests -B build/host-tests -G Ninja -DCMAKE_C_COMPILER=gcc
cmake --build build/host-tests
ctest --test-dir build/host-tests --output-on-failure
node --test tests/test_client.mjs
```

На стенде остаются power-cut на metadata и каждом этапе установки, повреждённые
и фрагментированные TCP-запросы под нагрузкой, несколько BL, обрыв связи,
повторные app/BL-переходы и проверка сохранности настроек/калибровки.

## Исправление Ethernet reset path

Путь warm reset зависит от корректной переинициализации Ethernet-периферии.

В текущей реализации bootloader сначала включает ETH clocks, а уже потом делает
force reset MAC в `LWIP/Target/ethernetif.c`.
Это исключает зависание в stale состоянии `MAC/DMA` после переходов
`bootloader -> app` и `app -> bootloader`.

## Сборка для вариантов модулей

Прошивка загрузчика **идентична для всех типов плат** — у всех общее ядро
(Ethernet PHY + статусный LED на PC8), а различающаяся секция ввода-вывода
загрузчиком не используется. Варианты отличаются **только** двумя
compile-time константами идентификации:

- `PRODUCT_ID` — уникален для типа платы (OTA требует точного совпадения)
- `HW_REVISION` — ревизия платы, `(major << 16) | (minor << 8) | patch`
  (OTA сравнивает **только** байт major)

Обе защищены `#ifndef` в `Application/flash/flash_map.h`: обычная сборка
использует дефолты, а `-DPRODUCT_ID` / `-DHW_REVISION` переопределяют их для
конкретного варианта.

### Схема PRODUCT_ID

`0x504C_CCTT` — `0x504C` = ASCII `"PL"` (маркер семейства PLCJS),
`CC` = число каналов (BCD), `TT` = код типа ввода-вывода.

| Вариант | Каналы | Тип I/O | PRODUCT_ID | HW_REVISION |
|---------|--------|---------|------------|-------------|
| `12di`  | 12 | Дискр. вход    (01) | `0x504C1201` | `0x010101` |
| `12do`  | 12 | Дискр. выход   (02) | `0x504C1202` | `0x010101` |
| `4rtd`  | 4  | RTD HW2.1 (ADS1220) | `0x504C0403` | `0x020100` |
| `4aic`  | 4  | Анал. вход ток  (04) | `0x504C0404` | `0x010101` |
| `4aiv`  | 4  | Анал. вход напр.(05) | `0x504C0405` | `0x010101` |
| `4ao`   | 4  | Анал. выход     (06) | `0x504C0406` | `0x010101` |
| `8aic`  | 8  | Токовые входы       | `0x504C0804` | `0x010101` |
| `8aoc`  | 8  | Токовые выходы      | `0x504C0806` | `0x010101` |

Таблица хранится в [`scripts/variants.csv`](scripts/variants.csv) — это единый
источник правды. Новая плата = одна новая строка.

### Сборка всех вариантов (рекомендуется)

```powershell
# Собрать все варианты в dist/ (BOOTLOADER_PLCJS_<name>_hw<MM.mm.pp>.hex)
./scripts/build_all.ps1

# Только один вариант
./scripts/build_all.ps1 -Variant 4rtd

# С чистой сборкой (очистить build-папки), Debug
./scripts/build_all.ps1 -Clean -Config Debug
```

Каждый вариант конфигурируется в свою папку `build/<name>-<config>`
(изолированный CMake-кеш — константы не «протекают» между вариантами),
результат `.hex` / `.bin` копируется в `dist/` с понятным именем.

### Ручная сборка одного варианта

```bash
cmake -S . -B build/4rtd -G Ninja \
      -DCMAKE_TOOLCHAIN_FILE=arm-none-eabi-toolchain.cmake \
      -DCMAKE_BUILD_TYPE=Release \
      -DPRODUCT_ID=0x504C0403 -DHW_REVISION=0x020100
cmake --build build/4rtd
```

Каждый результирующий `BOOTLOADER_PLCJS.bin` принимает OTA-образы только с
точно совпадающим `fw_header_t.product_id` и совпадающим байтом major в
`hw_revision`. Прошивка для неподходящего модуля отклоняется при
`FINALIZE_UPDATE` — до записи в область приложения.

## Заголовок прошивки

Начиная с этого релиза, валидные образы приложения должны встраивать `fw_header_t`
по адресу `APP_FLASH_BASE + 0x200` (смещение `0x200` в `app.bin`).

Цепочка валидации (три независимые проверки):

| Точка проверки | Файл | Что проверяется |
|---|---|---|
| `FINALIZE_UPDATE` | `fw_update_proto.c` | заголовок в **staging** flash |
| `INST_VERIFYING` | `fw_installer.c` | заголовок в **app** flash после копирования |
| `BOOT_VERIFY_APP` | `boot_main.c` | заголовок в **app** flash перед передачей |

Заголовок packed, 28 байт; размер и CRC в него не входят, они передаются в
параметрах OTA. HW заголовка — `(major<<8)|minor`, HW загрузчика —
`(major<<16)|(minor<<8)|patch`; сравниваются major, product ID совпадает точно.
Векторы staging проверяются как адреса исполнения application до его стирания.
MSP выровнен по 8 и не выходит выше `0x2001FFF0`; Reset_Handler имеет Thumb-бит
и лежит в фактическом образе. Проверка после копирования сохраняется.

`scripts/make_metadata.ps1` создаёт 340-байтную metadata для сектора 5 при
офлайн-прошивке приложения через SWD; это не генератор OTA-параметров.
Пакетная сборка `4rtd` выпускается для HW2.1, не для HW1.x.

### Сервисная прошивка через ST-Link (рекламации, отладка)

Штатный и единственный поддерживаемый путь — OTA. Начиная с 1.8 перед каждым
запуском загрузчик сверяет CRC установленного образа с размером и CRC из
metadata сектора 5, поэтому приложение, записанное по SWD без metadata (или с
чужой), не запускается: плата остаётся в загрузчике. Для сервисных случаев:

```powershell
./scripts/service_flash.ps1 -AppBin <app.bin>        # -DryRun только показывает команду
```

Скрипт проверяет векторы и `fw_header_t` образа, берёт product/hw/версию из
заголовка, строит metadata, затем программирует приложение (сектор 6–7) и в
последнюю очередь metadata (сектор 5), после чего сбрасывает плату. Загрузчик
(0–4), настройки (10) и калибровка 4RTD/8AIC/8AOC (11) не затрагиваются, полное
стирание не выполняется. Порядок безопасен при потере питания: если оборвать
запись между приложением и metadata, прежняя metadata не совпадёт по CRC, плата
останется в загрузчике и восстановится по OTA. Образ другого варианта (иной
product ID) загрузчик не запустит. Проверено на 4RTD HW2.1 с загрузчиком 1.8.

## Известные ограничения

- link-local адрес при старте не проверяется (адреса из PDP SET_NET проверяются
  с 1.9); найденные коллизии решаются адресным PDP
- watchdog в bootloader не включен
- аутентификация и контроль доступа для OTA-команд отсутствуют
- одновременно может быть подключен только один `Modbus TCP` клиент
- staging-область ограничена `256 KB`
